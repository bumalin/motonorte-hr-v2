**Summary.** Both tasks meet their acceptance criteria and I found no blocker or major issue.

**TASK-005 security posture (checked against architecture section 3 and ADR-009/010/011):**
- Passwords use scrypt (N=2^16, 16-byte salt) with a length-checked `timingSafeEqual`.
- An unknown or inactive user gets the same dummy verify and the same generic message. The throttle counts failures for nonexistent emails too, so neither timing nor wording reveals which accounts exist.
- Session tokens are 32 bytes from `randomBytes`, and only their SHA-256 is stored.
- The cookie is `HttpOnly; Secure; SameSite=Lax; path=/`. A new token is minted at every login, so there is no fixation path.
- Sliding expiry and deactivation are both enforced in `auth_get_session`. Logout deletes the row, and it runs as a POST Server Action, which Next protects with its Origin/Host check.
- Nothing logs passwords, hashes or tokens.
- There are no open redirects: both redirects go to fixed paths.
- `proxy.ts` uses the Next 16 name and only does an optimistic cookie check. `cookies()` and `headers()` are awaited.
- I confirmed that DATABASE_URL connects as `app_user` and that only `scripts/create-user.ts` uses the owner URL, as Data Model note 5 requires.
- No app code queries outside `withUser`/`withAnon`.
- No new dependencies were added.

**Checks run:** `npm test` (42 pass), typecheck, lint and `db:verify` (including the throttle, reset, session and logout checks) are all green. The auth tests would fail if verify accepted wrong passwords or if the token and its hash were confused.

**TASK-006:**
- The shell matches UX section 1: sidebar, name + role badge, Sign out, "This week" shortcut, `aria-current`, and a global `:focus-visible` outline.
- The format helpers are correct: true minus sign plus danger colour, UTC formatting of ISO calendar dates so days do not shift, Manila "today", and all three week-label shapes.

The minors are worth fixing opportunistically. The per-email advisory lock on login is the one I would do first.
